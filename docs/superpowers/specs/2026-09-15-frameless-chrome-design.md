# PiecePool Desktop — 프레임리스 창 크롬 — 설계

- 날짜: 2026-09-15
- 상태: 설계 승인됨 (구현 계획 대기)
- 상위 문서: `2026-09-05-electron-rebuild-design.md` — 재구축 전체 설계. 이 문서는 그 **7단계(Electron 셸)** 를 다룬다.
- 선행: `2026-09-14-real-vault-design.md` — 실제 볼트 열기. 그 조각이 끝나 앱이 실물 트리를 그리게 된 뒤에 드러난 문제다.

## 1. 무엇을 만드나

OS 가 그리는 타이틀바를 없애고, 창 조작과 드래그를 앱이 직접 맡는다.

지금은 창 맨 위에 `PiecePool` 타이틀바가 있고, 그 높이만큼 **리본 토글 버튼이 아래로 밀려 있다.**
옵시디언은 타이틀바가 없어서 리본이 창 맨 위(y=0)에서 시작한다. 그 차이를 없애는 것이 이 조각이다.

창 크기·위치 기억은 범위 밖이다. 이 조각은 크롬의 **모양과 조작**만 다룬다.

## 2. 결정 넷

| 항목          | 결정                                                                     | 기각한 것                                | 근거                                                    |
| ------------- | ------------------------------------------------------------------------ | ---------------------------------------- | ------------------------------------------------------- |
| 프레임        | **타이틀바를 없앤다.** 창 조작 버튼은 직접 그린다 (macOS 만 예외 — §2.1) | Windows Controls Overlay / 타이틀바 유지 | 모양을 완전히 통제한다. 옵시디언과 같은 선택            |
| 플랫폼        | **Windows·macOS 둘 다 지금 맞춘다**                                      | Windows 먼저, macOS 는 나중              | 관례가 정반대라 나중에 붙이면 레이아웃을 다시 짜야 한다 |
| 최대화 아이콘 | **바꾸지 않는다.** 고정 아이콘 하나                                      | 최대화 시 "복원" 모양으로 교체           | 역방향(main→renderer) 채널이 구조를 하나 늘린다         |
| 드래그 영역   | **상단 32px 띠 통째**                                                    | 사이드바 헤더만                          | 사이드바를 접어도 창을 움직일 수 있어야 한다            |

### 2.1 플랫폼이 갈리는 이유

창 조작 버튼의 관례가 정반대다 — Windows 는 오른쪽 위 세 버튼, macOS 는 왼쪽 위 신호등.
한 설정으로 덮을 수 없으므로 창 생성에서 갈린다.

| 플랫폼        | 설정                                               | 창 조작 버튼                         |
| ------------- | -------------------------------------------------- | ------------------------------------ |
| Windows·Linux | `frame: false`                                     | **우리가 그린다** (오른쪽 위)        |
| macOS         | `titleBarStyle: "hidden"` + `trafficLightPosition` | **OS 신호등** (왼쪽 위, 위치만 조정) |

macOS 에서 `frame: false` 를 쓰면 **신호등까지 사라진다.** `titleBarStyle: "hidden"` 은 바만 없애고 신호등을 남기므로,
관례를 지키면서 리본이 y=0 에서 시작한다. 신호등이 리본 버튼과 겹치므로 `trafficLightPosition` 으로 내려 앉힌다.

즉 **macOS 에서는 우리 버튼을 그리지 않는다.** 그리면 신호등과 둘 다 뜬다.

### 2.2 최대화 아이콘을 고정으로 두는 이유

Windows 앱은 보통 최대화 상태일 때 버튼 아이콘이 "복원" 모양으로 바뀐다.
그러려면 renderer 가 최대화 여부를 알아야 하는데, 지금 `PiecePoolApi` 는 **invoke 단방향뿐**이다.

역방향 채널을 만들면 `webContents.send` 와 renderer 쪽 구독·구독 해제가 따라오고,
`shared/ipc.ts` 의 계약 모양이 "요청→응답" 하나에서 둘로 늘어난다.
아이콘 한 개를 위해 치를 값이 아니다. 필요해지면 그때 만든다.

## 3. IPC 계약

`src/shared/ipc.ts` 에 채널 셋을 더한다. 셋 다 **인자 없음, 반환 없음**이다.

```
window:minimize · window:toggleMaximize · window:close
```

renderer 는 여전히 아무 값도 보내지 않는다 — 실제 볼트 조각이 세운 "renderer 는 경로를 보내지 않는다" 를 그대로 잇는다.

`main/ipc.ts` 의 핸들러는 `BrowserWindow.fromWebContents(e.sender)` 로 요청한 창을 찾아 조작한다.
창을 모듈 변수로 쥐지 않는다 — 창이 여럿이 될 때 조용히 틀리는 자리다.

`wrap()` 을 쓰지 않는다. `wrap()` 은 `Result<T>` 를 만드는데 이 셋은 돌려줄 값이 없다.
대신 `ipcMain.on` 을 쓴다 — 응답이 없는 단방향이라는 것을 타입이 아니라 API 선택으로 드러낸다.

### 3.1 `shared/ipc.ts` 는 FROZEN 이다

이 파일은 바로 앞 조각에서 `// FROZEN: 파일 전체. 변경 시 상대 개발자와 합의` 로 표시했다.
채널 셋을 더하는 것은 정확히 그 합의가 필요한 변경이고, **2026-09-15 대화에서 합의했다.**

## 4. 레이아웃

창 맨 위 32px 띠 전체가 `-webkit-app-region: drag` 다.
그 위에 얹히는 것들은 전부 `no-drag` 로 되돌린다:

- 리본 토글 버튼
- 사이드바 헤더(볼트 이름)
- 창 조작 버튼 셋

### 4.1 드래그 영역은 마우스 이벤트를 삼킨다

**이 조각에서 가장 조용히 깨지는 자리다.**

드래그 영역 위에 있는데 `no-drag` 를 안 붙인 버튼은 **클릭이 아예 안 먹는다.**
화면상으로는 멀쩡해 보이고, 눌러 봐야만 드러난다. 렌더 예외도 콘솔 경고도 없다.

리본 버튼이 정확히 이 위험에 있다 — 창 맨 위 32px 안에 들어가기 때문이다.

## 6. 통과 조건

단위 테스트가 닿지 않는다. 창 조작도 드래그도 OS 경계이고,
`vitest.config.ts` 는 `environment: "node"` 이며 이 레포는 "화면은 사람이 본다"(CLAUDE.md §7).

정적 검사 넷(`prettier --check` · `lint` · `typecheck` · `test`)이 통과하고 테스트 수가 그대로인 것은 필요조건일 뿐이다.

**통과 조건은 사람이 직접 확인하는 것이다:**

- 리본 토글 버튼이 창 맨 위에서 시작하나 (타이틀바가 사라졌나)
- 리본 토글 버튼이 **눌리나** (§4.1)
- 상단 띠의 빈 곳을 잡아 창이 움직이나
- 사이드바를 접은 상태에서도 창이 움직이나
- 최소화·최대화·닫기 세 버튼이 각각 동작하나
- 상단 띠를 더블클릭하면 최대화되나 (Windows 가 공짜로 해 준다)
