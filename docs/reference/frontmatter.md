# 프론트매터

> 정본은 [ADR-0002](../adr/0002-agentic-pipeline.md) 결정 5·6 다. 이 문서는 필드별 상세를 담는다.
> 전체 흐름은 [파이프라인 설명서](../파이프라인-설명서.md) 에 있다.

프론트매터는 두 종류다.

| 종류                 | 어디에          | 무엇                       |
| -------------------- | --------------- | -------------------------- |
| **일반 위키 페이지** | `wiki/*.md`     | 주제 하나를 다루는 페이지  |
| **출처 페이지**      | `sources/@*.md` | 원본 파일 하나의 추출 전문 |

**사용자 노트에는 붙이지 않는다.** 제품 원칙 4 에 따라 사용자가 쓴 파일은 우리가 건드리지 않는다. 볼트 안 노트의 처리 이력은 `.piecepool/sync_state.json` 에 둔다.

# 일반 위키 페이지 — 5필드

```yaml
---
aliases: [김 대리, 김민수]
sources: ["[[회의/2026-09-01]]", "[[@회의록-0901]]"]
created: 2026-09-01
compiledAt: 2026-09-07T09:12:00+09:00
hashes:
  요약: a1f3c9e2
  나와의 관계: 7b2d4e91
  기록: 3551b4b6
---
```

전부 optional 이다. 임의의 옵시디언 볼트를 열면 프론트매터가 아예 없는 파일이 있고, 그것도 똑같이 유효해야 한다.

## `aliases`

- **하는 일**: 같은 것의 다른 이름을 모은다. `[[김 대리]]` 가 `김대리.md` 로 해석되게 한다
- **누가 쓰나**: AI 가 추출하고 코드가 합집합으로 누적한다. 사용자도 추가할 수 있다
- **언제 바뀌나**: 정리할 때마다 합집합으로 늘어난다. 줄어들지 않는다
- **어디에 쓰이나**: 링크 해석, 검색 색인, 같은 것인지 판정
- **없으면**: "김대리"와 "김 대리"가 별개 페이지가 된다. 위키가 중복으로 폭발한다

### 추가되지 않는 경우

빌더가 세 가지를 검사하고, 하나라도 걸리면 추가하지 않는다.

| 조건                            | 왜                                                      |
| ------------------------------- | ------------------------------------------------------- |
| 다른 페이지의 **파일명**과 같다 | 파일명이 항상 이기므로 그 별칭은 영원히 작동하지 않는다 |
| 다른 페이지의 **별칭**과 같다   | 충돌이 생겨 양쪽 링크가 모두 해제된다                   |
| 자기 자신의 파일명과 같다       | 무의미하다                                              |

### 링크 해석 순서

```
1. 정규화한 파일명이 일치한다        → 그 페이지. 끝.
2. 정규화한 별칭 일치가 하나다        → 그 페이지
3. 별칭 일치가 둘 이상이다            → 링크 해제 (괄호만 벗긴다)
4. 일치가 없다                       → 링크 해제
```

정규화는 `normalizeTitle()` 하나만 쓴다. NFC 정규화 + 소문자 변환 + 공백 정리를 한다.

**NFC 정규화가 필요한 이유**: macOS 옵시디언은 파일명을 NFD(자음과 모음이 분리된 형태)로 저장하는 경우가 있다. 본문의 `[[김대리]]` 는 NFC 로 들어오므로, 정규화 없이 비교하면 같은 단어인데 일치하지 않는다.

## `sources`

- **하는 일**: 이 페이지에 정보를 준 출처 목록
- **누가 쓰나**: 코드만. `addSource()` 로만 건드린다
- **언제 바뀌나**: 정리할 때마다 합집합으로 늘어난다. **줄어들지 않는다**
- **어디에 쓰이나**: 근거 추적, 검색 결과 표시
- **없으면**: 정보가 어디서 왔는지 알 수 없다

### 두 종류가 섞인다

| 소스                    | 값                                              |
| ----------------------- | ----------------------------------------------- |
| 볼트 안 사용자 노트     | `[[회의/2026-09-01]]` — 노트를 직접 가리킨다    |
| 볼트 밖에서 들어온 파일 | `[[@회의록-0901]]` — **출처 페이지**를 가리킨다 |

둘 다 실재하는 마크다운 파일이므로 링크가 깨지지 않는다. 위키 페이지 입장에서는 구분할 필요가 없다.

### 세션 로그도 여기 들어간다

`CLAUDE.md` 의 이름 충돌 표에 있는 내용이다. `sources/` 폴더(원본 파일)와 `Fm.sources`(프론트매터 필드)는 다른 것이고, 후자에는 `.piecepool/sessions/` 의 세션 로그도 들어간다.

```ts
fm.sources = [...];      // 하지 마라. 타입은 통과하고 상대의 출처가 사라진다
addSource(fm, "...")     // 이렇게
```

`setSources` 는 일부러 만들지 않았다. 덮어쓰는 경로를 아예 없앤 것이다.

## `created`

- **하는 일**: 페이지가 처음 생긴 날
- **누가 쓰나**: 코드가 1회. 한 번 적으면 바뀌지 않는다
- **어디에 쓰이나**: 표시용, 정렬
- **없으면**: 페이지가 생긴 시점을 잃는다

## `compiledAt`

- **하는 일**: AI 가 마지막으로 정리한 시각. **어느 기록까지 반영했는가**
- **누가 쓰나**: 코드만. 정리가 성공해야 갱신한다. 실패하면 옛 값을 유지한다
- **어디에 쓰이나**: 손편집된 절에 새 기록만 골라 덧붙일 때 **이 시각 이후의 기록만** 대상이 된다
- **없으면**: 손편집된 절에 무엇을 덧붙일지 알 수 없다. 전부 덧붙이면 중복되고, 아무것도 안 덧붙이면 새 정보가 누락된다

### `hashes` 와 짝이다

```
hashes    → "이 절을 건드리면 안 된다"를 안다
compiledAt → "그렇다면 새 기록만 어디부터 덧붙일까"를 안다
```

둘 중 하나만 있으면 손편집 보호가 반쪽만 작동한다.

### 파일 수정 시각과 다르다

`compiledAt` 은 우리 코드가 프론트매터에 적는 값이다. 파일 시스템의 수정 시각이 아니다. 그래서 볼트를 git 이나 클라우드로 동기화해서 파일 시각이 왜곡되어도 영향을 받지 않는다.

## `hashes`

- **하는 일**: `## 절` 각각의 내용 해시. sha256 앞 8자리
- **누가 쓰나**: 코드만. **AI 가 쓴 절에만 찍는다.** 사용자가 고친 절에는 새 지문을 찍지 않는다
- **어디에 쓰이나**: 손편집 보호, 트랜잭션 선행조건 검사
- **없으면**: **손편집 보호가 통째로 무력화된다.** AI 가 매 정리마다 사용자가 고친 글을 덮는다. 제품 원칙 3 을 직접 위반한다

### 작동 방식

```
1. 정리 직후 각 절의 내용을 해시해서 적는다

2. 다음 정리 때 그 절의 현재 내용을 다시 해시한다

3. 판정
     지문이 같다   → AI 가 쓴 그대로다   → 자유롭게 다시 쓴다
     지문이 다르다  → 사용자가 고쳤다     → 그 절을 건드리지 않는다
     지문이 없다   → 모른다             → 글이 있으면 지킨다
```

### H2 단위로 찍는다

```markdown
## 주요 사건들 ← 이 절의 해시를 찍는다

### 서버 장애 ← 부모 H2 의 해시에 포함된다

#### 타임라인 ← 부모 H2 의 해시에 포함된다
```

`### 서버 장애` 안의 한 줄을 사용자가 고치면 부모인 `## 주요 사건들` 전체가 보호된다. 보호 범위가 약간 넓어지지만 사용자 글을 지키는 방향이므로 안전한 쪽이다.

### 지킨 절에 지문을 찍지 않는 이유

찍으면 다음 정리에서 글자와 지문이 맞아떨어져 "우리 글"로 판정되고 덮인다. **사용자 글이 정리 한 번만 버티게 된다.**

### 절 이름이 바뀌어도 보호된다

```
hashes 에 {주요 사건들: c7d2e1f0} 이 적혀 있다
사용자가 절 이름을 "주요 사건" 으로 바꾼다

다음 정리 때
  "주요 사건들" → 파일에 없다 → 고아 지문이므로 무시한다
  "주요 사건"   → 지문이 없다 → 세 번째 규칙 → 글이 있으니 지킨다
```

**새 장치가 필요 없다.** "지문이 없으면 지킨다"가 이름 변경까지 커버한다.

### 기록 절은 예외다

```
기록 절의 지문이 다르다 = 사용자가 기록 줄을 고쳤다

  기존 기록 줄  → 건드리지 않는다
  새 기록       → 맨 아래에 덧붙인다 (중복이 아닌 경우만)
  지문          → 갱신하지 않는다
```

기록은 자유절과 성격이 다르다. 자유절은 다시 쓸 수 있지만 기록은 덧붙이기만 한다. 사용자가 오타를 고쳤더라도 새 사실이 계속 쌓여야 한다.

### 왜 `.piecepool/` 에 두지 않는가

|                                    | 재계산할 수 있는가          |
| ---------------------------------- | --------------------------- |
| 절의 현재 해시                     | 파일을 읽어 계산하면 된다   |
| **우리가 마지막으로 쓴 글의 해시** | **파일에서 뽑아낼 수 없다** |

파생 캐시가 아니라 **재계산이 불가능한 상태**다. 지우면 손편집 보호가 오판하고, 오판의 방향이 사용자 글을 덮는 쪽이다.

되돌리기가 파일 단위인 것도 근거다. 본문과 지문이 다른 파일에 있으면 한쪽만 복원됐을 때 어긋나고, 안전망이 안전망을 깨뜨린다.

# 출처 페이지 — 5필드

```yaml
---
type: source
raw: "[[sources/회의록-0901.pdf]]"
raw_hash: 01643e28
date: 2026-09-01
created: 2026-09-10
---
```

**볼트 밖에서 들어온 소스만 만든다.** 볼트 안 사용자 노트는 이미 마크다운이고 볼트 안에 있으므로 만들지 않는다.

**코드가 조립한다.** 추출 전문을 그대로 담으므로 무엇을 남기고 버릴지 판단할 일이 없고, 판단이 없으면 AI 를 부를 이유가 없다.

## `type`

- **값**: `source` 고정
- **하는 일**: 이 페이지가 출처 페이지임을 나타낸다
- **왜 폴더 경로로 판별하지 않나**: 옵시디언 사용자는 폴더를 수시로 옮긴다. 경로는 사용자가 바꿀 수 있는 값이고, 프론트매터 필드는 우리가 관리하는 값이다. 제품 원칙 4 에 따라 사용자가 폴더를 옮기는 것을 막지 않으므로, 경로에 의존하면 추적을 잃는다. `sources/` 는 기본 자리일 뿐이고 판별 기준이 아니다

## `raw`

- **하는 일**: 원본 파일로 가는 링크
- **누가 쓰나**: 코드
- **없으면**: 원본을 찾을 수 없다

## `raw_hash`

- **하는 일**: **처리했을 당시** 원본 파일의 지문 (sha256 앞 8자리)
- **누가 쓰나**: 코드
- **어디에 쓰이나**: 입력 벽의 중복 판정

```
같은 파일이 다시 들어왔다

  지문이 같다        → 원본이 그대로다     → 건너뛴다
  지문이 다르다      → 원본이 수정되었다   → 다시 처리한다
  출처 페이지가 없다  → 처음 보는 파일이다  → 새로 처리한다
```

- **없으면**: 이미 처리한 파일을 또 처리해서 기록이 중복으로 쌓인다

`hashes` 와 같은 논리로 볼트 안에 있어야 한다. 원본을 지금 다시 해시할 수는 있지만, **"우리가 처리했을 당시 원본이 무엇이었나"** 는 재계산할 수 없다.

## `date`

- **하는 일**: 출처가 기록된 날. 기록 줄의 날짜가 여기서 나온다
- **누가 쓰나**: 코드. 사용자가 고칠 수 있다
- **`null` 이 될 수 있다**

### 어떻게 얻나

```
[볼트 안 .md]     프론트매터 created → 파일명 패턴 → 파일 수정 시각
[PDF·음성·기타]   파일명 패턴 → 파일 내부 메타데이터 → 파일 수정 시각 → null
```

파일명 패턴은 신뢰도를 나눈다.

| 패턴                     | 판정                                         |
| ------------------------ | -------------------------------------------- |
| `2026-09-01`, `20260901` | 확정한다                                     |
| `260901`                 | 대체로 안전하다                              |
| `0901` 단독              | **연도를 모른다.** 다음 단계로 넘긴다        |
| `2026` 단독              | **날짜가 아니라 연도다.** 다음 단계로 넘긴다 |

`2026년_사업계획서.pdf` 를 2026년 1월 1일로 만들면 시계열이 조용히 오염된다.

### `null` 일 때

기록 줄에 `(날짜 미상)` 을 적고 기록 절 맨 아래에 모은다.

```markdown
## 기록

- 2026-09-01 QA 담당이다 ← [[@회의록-0901]]
- (날짜 미상) 커피를 좋아한다 ← [[@스캔문서]]
```

**인입한 날짜를 대신 쓰지 않는다.** "우리가 받은 날"은 "출처가 기록된 날"과 다른 값인데, 기록 줄에 박아 놓으면 맞는 값처럼 보인다. 조용히 틀리고, 틀렸다는 사실을 아무도 알 수 없다.

사용자가 나중에 이 필드를 고치면 다음 정리에서 기록 줄이 갱신된다.

## `created`

- **하는 일**: 출처 페이지를 만든 날
- **누가 쓰나**: 코드가 1회
- **어디에 쓰이나**: 표시용

## 파일명 규칙

```
sources/회의록-0901.pdf  →  sources/@회의록-0901.md
```

`@` 접두사를 붙이는 이유는 셋이다. 같은 폴더의 원본 파일과 눈으로 구분되고, 정렬했을 때 추출물이 한곳에 모이며, `[[@회의록-0901]]` 링크만 봐도 출처를 가리킨다는 것이 드러난다.

**날짜를 파일명에 넣지 않는다.** `date` 가 `null` 일 수 있으므로 이름 규칙을 따로 정해야 하고, 나중에 날짜를 알게 되어 파일명을 바꾸면 그것을 가리키던 링크를 모두 고쳐야 한다.

이름이 겹치면 숫자를 붙인다.

```
Downloads/회의록.pdf   →  sources/@회의록.md
Desktop/회의록.pdf     →  sources/@회의록-2.md
```

원본 파일명에 운영체제 금지 문자가 있으면 출력 벽이 제거한다.

# 뺀 필드와 근거

초판 ADR-0002 가 정한 12필드에서 일곱 개를 뺐다. 근거는 [ADR-0002 의 기각한 대안](../adr/0002-agentic-pipeline.md#기각한-대안) 에 있다.

| 뺀 필드     | 한 줄 근거                                                                   |
| ----------- | ---------------------------------------------------------------------------- |
| `title`     | 파일명이 유일한 식별자다. 두면 사용자가 파일명을 바꿨을 때 어긋난다          |
| `updated`   | 앱 편집기와 AI 가 번갈아 건드리면 신뢰도를 잃는다. 시스템 로직이 읽지 않는다 |
| `type`      | `entity`/`topic` 구분을 코드가 강제할 이유가 없다                            |
| `kind`      | AI 추천 + 사용자 선택이면 프론트매터가 아니라 UI 기능이다                    |
| `relation`  | "나와의 관계" 한 구절. 본문에 들어가도 된다                                  |
| `tags`      | 사용자가 직접 다는 것이므로 코드가 관리할 필드가 아니다                      |
| `contested` | 검문 단계에서 잡으면 되고 파일에 영구히 남길 필요가 없다                     |

## `name` 은 프론트매터 필드가 아니다

AI 가 내놓는 JSON 에는 `pages[].name` 이 있다. 빌더에게 "이 이름으로 파일을 만들라"고 알려주는 값이고, **저장될 때 파일명이 되며 프론트매터에는 들어가지 않는다.**

`title` 을 뺀 결정과 짝이 맞는다. 파일명이 유일한 식별자이므로 같은 값을 프론트매터에 또 적지 않는다.

---

일반 위키 페이지의 `type` 은 뺐지만 **출처 페이지의 `type: source` 는 남았다.** 전자는 코드가 분기에 쓰지 않는 분류였고, 후자는 코드가 "이 파일이 출처 페이지인가"를 판별하는 데 쓴다.

---

# 볼트 안 노트의 처리 이력

사용자 노트에는 프론트매터를 쓸 수 없으므로 별도 파일에 둔다.

`.piecepool/sync_state.json`

```json
{
  "version": 1,
  "notes": {
    "회의/2026-09-01.md": {
      "hash": "01643e28",
      "compiledAt": "2026-09-07T09:12:00+09:00"
    }
  }
}
```

| 상황            | 판정                                                                     |
| --------------- | ------------------------------------------------------------------------ |
| 목록에 없다     | 처음 보는 노트다. 정리한다                                               |
| 지문이 같다     | 바뀌지 않았다. 건너뛴다                                                  |
| 지문이 다르다   | 수정되었다. 다시 정리한다                                                |
| 파일이 사라졌다 | 사용자가 지웠다. 항목을 정리하고, 그 노트에서 나온 기록 줄에 표시를 단다 |

## 왜 이것은 `.piecepool/` 에 둘 수 있나

기준은 "재계산 가능한가"가 아니라 **"잃었을 때 원칙을 위반하는가"** 다.

| 잃으면            | 무슨 일이 벌어지나                                    |
| ----------------- | ----------------------------------------------------- |
| 위키의 `hashes`   | 사용자가 고친 글이 덮인다. **복구 불가능한 손실이다** |
| `sync_state.json` | 이미 정리한 노트를 다시 정리한다. AI 호출이 낭비된다  |

후자의 피해는 두 장치가 막는다. 위키 본문은 `hashes` 가 사용자 편집 절을 보호하고, 기록 줄은 중복 체크(`date` + 정규화한 `fact` + `source`)가 같은 기록을 걸러낸다.

## 출처가 삭제되었을 때

기록 줄을 지우지 않고 표시만 단다.

```markdown
- 2026-09-01 QA 담당이다 ← [[회의/2026-09-01]] (출처 삭제됨)
```

사용자가 노트를 지운 의도가 둘 중 무엇인지 알 수 없기 때문이다.

| 의도                                         | 원하는 동작   |
| -------------------------------------------- | ------------- |
| 원본은 필요 없지만 뽑아낸 사실은 남기고 싶다 | 기록을 남긴다 |
| 내용이 틀렸으니 파생된 것도 지우고 싶다      | 기록도 지운다 |

모르면 파괴하지 않는다. 남긴 것은 나중에 지울 수 있지만 지운 것은 되돌릴 수 없다. 사용자가 실수로 지웠다가 복구하는 경우도 있다.

`[[링크]]` 를 그대로 두고 문구만 덧붙이는 이유는, 사용자가 노트를 복구하면 **표시만 지우면 링크가 되살아나기** 때문이다. 대괄호를 벗기면 "원래 링크였다"는 정보가 사라져 복구할 수 없다.

정리할 때마다 사용자에게 묻지 않는다. 제품 원칙 2 를 어긴다. `npm run wiki:lint` 가 목록으로 보고한다.
