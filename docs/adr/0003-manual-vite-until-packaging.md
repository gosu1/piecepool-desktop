# ADR-0003 — 패키징 전까지 vite 를 손으로 설정한다

- 날짜: 2026-09-15
- 상태: 제안됨
- 대체: [재구축 설계](../superpowers/specs/2026-09-05-electron-rebuild-design.md) §2.1 의 선택지 **B(electron-vite)** 를 **패키징 시점까지 유예**한다. 폐기가 아니다.

## 이 문서를 읽는 법

- **굵은 한 줄이 결정이고, 그 아래가 근거다.**
- 이 ADR 은 이미 벌어진 이탈을 사후에 기록한다. 세 조각에 걸쳐 흘러온 것을 한자리에 모은다.
- **유예이지 폐기가 아니다.** 되돌아갈 조건을 §되돌아가는 시점 에 적어 둔다.

---

## 맥락

### 원래 무엇을 정했었나

재구축 설계 §2.1 이 빌드 배선을 세 가지로 놓고 하나를 골랐다.

| 안  | 내용                             | 판정   | 근거                                               |
| --- | -------------------------------- | ------ | -------------------------------------------------- |
| A   | npm workspaces 모노레포          | 비채택 | 독립 배포·버전의 이득이 단일 데스크톱 앱에 없다    |
| B   | 단일 패키지 + **electron-vite**  | 채택   | 설정 하나로 main·preload·renderer 3타깃을 처리한다 |
| C   | 단일 패키지 + **Vite 수동 설정** | 비채택 | "아낀 의존성보다 잃는 시간이 크다"                 |

C 를 기각한 근거는 셋이었다 — **main/preload 번들링**, **HMR**, **네이티브 모듈 externalize** 를 직접 관리해야 한다는 것.

### 실제로는 무엇이 되었나

7·8단계를 진행하면서 세 번에 걸쳐 C 에 가까운 상태가 되었다.

1. **빈 셸** — Electron 44 가 `.ts` 엔트리를 그대로 실행하므로 번들러 없이 창이 떴다. electron-vite 도입을 미뤘다
2. **좌측 크롬** — Tailwind v4 를 들이면서 `vite.config.ts` 를 renderer 전용으로 추가했다
3. **실제 볼트 열기** — 샌드박스 preload 가 단일 CommonJS 를 요구하므로 `vite.preload.config.ts` 를 하나 더 두기로 했다

즉 지금 상태는 **설정 파일 둘 + 번들하지 않는 main** 이다.

## 결정

**패키징을 시작할 때까지 vite 를 손으로 설정한다. electron-vite 는 그 시점에 도입한다.**

### 왜 — 기각 근거 셋 중 하나가 사라졌다

C 를 기각한 세 근거 중 **main/preload 번들링** 의 절반이 성립하지 않는다.

Electron 44 에 내장된 Node 가 타입 스트리핑을 지원해 `src/main/index.ts` 를 **번들 없이 그대로 실행한다.** 설계가 쓰인 2026-09-05 시점에는 없던 선택지다. `package.json` 의 `"main"` 이 `.ts` 를 직접 가리키고, 번들 설정이 0 줄이다.

preload 는 여전히 번들이 필요하지만, 단일 파일 lib 모드 15 줄로 끝난다. 남는 비용이 **설정 파일 두 개, 약 25 줄**이다.

### 무엇을 포기했나

- **main·preload 의 HMR 이 없다.** 고칠 때마다 `npm start` 를 다시 친다. 둘 다 자주 바뀌지 않으므로 견딘다
- **프로덕션 빌드 경로가 없다.** `main` 이 `http://localhost:5173` 을 상수로 물고 있다. 개발 전용 상태다
- **네이티브 모듈 externalize 규칙이 없다.** 지금 네이티브 의존성이 하나도 없으므로 문제가 드러나지 않는다

셋 다 **미뤄 둔 것이지 풀린 것이 아니다.**

## 되돌아가는 시점

아래 중 **하나라도** 해당하면 electron-vite 를 도입한다. 그때 이 ADR 은 대체된다.

- **패키징을 시작할 때** — asar 포장과 프로덕션 `file://` 경로가 필요해진다. 가장 유력한 계기다
- **네이티브 의존성이 들어올 때** — externalize 규칙을 손으로 관리하기 시작하면 기각 근거가 그대로 살아난다
- **vite 설정 파일이 셋을 넘을 때** — "설정 하나" 라는 B 의 이점이 실질이 된다
- **main 이나 preload 를 자주 고치게 될 때** — HMR 부재가 실제 비용이 된다

재구축 설계 §2.2 의 트리에 있는 `electron.vite.config.ts` 와 `electron-builder.yml` 은 **여전히 유효한 목적지다.** 지금 없을 뿐이다.

## 기각한 대안

- **지금 곧바로 electron-vite 로 전환** — 진행 중인 기능 조각("폴더 고르기")에 빌드 시스템 교체가 겹친다. 무언가 깨졌을 때 원인이 둘이 되고, 전환의 실질적 이득(패키징·네이티브·프로덕션 경로)은 아직 범위 밖이다
- **설계 §2.1 을 개정해 C 를 정식 채택** — B 를 폐기하는 것이 되는데, 폐기할 근거가 없다. 기각 근거 셋 중 둘은 패키징 시점에 그대로 돌아온다
- **preload 를 손으로 `.cjs` 로 작성** — 번들러가 아예 필요 없어지지만, 앱의 공격 표면 전체인 파일 하나만 TypeScript 밖에 남고 `shared/` 의 계약 타입을 쓸 수 없게 된다

## 영향

- `CLAUDE.md` §9 표에 이 ADR 을 가리키는 줄을 더한다
- 재구축 설계 §2.1 은 **고치지 않는다.** 그 문서는 목적지를 적은 것이고, 이 ADR 이 현재 위치와 유예 사유를 적는다
