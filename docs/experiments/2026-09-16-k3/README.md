**1. 링크의 1/3 이 같은 이름의 반복이다 — 코드 문제.** K3 회차의 본문 링크 345~~382 중 125~~164 가 한 페이지 안에서 같은 이름을 다시 건 것이다. `autoLink` 가 이름이 나올 때마다 걸어서 `[[환각]] 비율이 … 숫자 [[환각]]은 … [[환각]] 14.0%` 처럼 된다. 허브 뺀 밀도 5.5 (flash-lite 2.6) 의 절반이 이것이고 읽기에 거슬린다. 절마다 첫 등장만 거는 것이 맞다 — 정답 세트(두 페이지가 이어졌나)에는 영향이 없으므로 이 실험이 끝난 뒤 코드로 고친다.

꼴이 일정하다: **열린 음절에 받침이 붙는다.** 해→핵·합, 무→묵·물, 르→륵·륾, 내→낸·남, 체→척·철, 아무→아묵·아묘. `해법` 은 32회차에서 8번 `핵법`, 35회차에서 10번 `핵볍` 이 됐다. 같은 낱말이 회차마다 다른 꼴로 깨지는 것을 보면 하위 음절 토큰 위에서의 샘플링(K3 는 온도 1.0 고정)이 원인으로 보인다. **effort high 에서도 같은 오타가 난다** (39회차 quote: 아묘도·다륾면·낸년·합볼). 추론 깊이의 문제가 아니라 디코딩의 문제다. 이 목록은 눈에 띈 것만이라 실제는 더 많다.

이것이 오늘 가장 값나가는 발견이다. 한국어 제품에서 본문에 `핵볍` 이 열 번 찍히는 것은 정답 세트 100% 보다 먼저 보인다. 대책 후보 (이 실험 뒤에):

- 절 본문의 한글 낱말 중 원문(노트+기존 페이지)에 없고, 받침 하나만 다른 낱말이 원문에 있으면 그것으로 되돌린다 — 새 종류의 벽. 모델 글을 고치는 것이라 좁게 (받침 추가만, 원문에 있는 낱말로만)
- quote 대조도 같은 규칙으로 좁게 허용해 기록 10~20줄을 되찾는다
- Moonshot 에 재현 사례를 보낸다 (`해법` 한 단어로 재현될 것이다)

시제품(`batchim.py`): 본문의 한글 어절 중 원문 어휘에 없고 한 음절의 받침을 빼면 원문 어휘에 있는 것을 찾았다. 32회차에서 후보 50곳 중 진짜 깨짐이 20곳(핵법이 6 · 낸년 5 · 낸내 2 · 핵법 2 · 물난해서 · 자륵면 · 다륾면 · 따륵면 · 아묵도), 나머지는 활용형(정했다→정해다)을 잘못 잡은 것이다. **사전 없이는 본문 쪽 벽을 못 세운다** — hunspell-ko 같은 사전이 있어야 한다. quote 쪽은 원문이 곧 사전이라 사전 없이 된다: 노트에 있는 구절과 받침 하나만 다른 quote 는 통과시키고 **기록 줄에는 노트의 글자를 쓴다** (모델 글을 고치는 것이 아니라 원문으로 되돌리는 것). 이 실험 뒤에 만든다.

**4. 주제 페이지가 비대해진다.** `한국어 요약의 환각 측정과 완화`(연구 주제 자체)와 `환각` 이 회차마다 5~~8천 자·30~~46 기록으로 가장 크다. 30장 볼트가 한 주제이니 자연스럽지만, 이 두 장은 사실상 두 번째 허브다. 축소 프롬프트(38)에서 7,752자로 더 커진 것은 페이지를 덜 만들수록 여기로 쏠린다는 뜻이다. 규모(500장)에서 이 페이지가 어떻게 되는지가 실제 노트 단계에서 볼 것 하나.

**5. 이름은 첫 명명에서만 흔들린다.** K3 세 회차의 페이지 이름 합집합 45 중 셋 다 있는 것은 25. 나머지는 거의 같은 것의 다른 이름이다 — `Roit et al. 2023` / `NLI 보상 RL` / `RLHF 환각 줄이기` (같은 논문), `교수님` / `최교수님`, `소연` / `소연이`, `exp-001` / `exp-001 KoBART 재현`, `부모님` / `가족`. 한 회차 안에서는 같은 것이 두 장이 된 적이 없다 (`이름 겹침 의심` 0~1). 즉 처음 이름을 정할 때만 흔들리고, 한 번 정해지면 이후 노트는 `<관련 위키>` 의 이름을 따라간다. 제품(한 볼트가 시간에 걸쳐 자라는 것)에는 이쪽이 중요하다.

**6. `나` 허브.** K3 세 회차 모두 `나` 에 기록 0~~1 (규칙 7 준수, flash-lite 는 6~~7), 링크 43~45, 요약은 20장째 갱신에서 현재("exp-007 로 14.0%까지")를 말한다.

## 관찰

- **K3 는 느리다.** effort low 에서 호출당 37~57초 (flash-lite 는 몇 초). 30장이면 25분, 86장이면 한 시간. 제품에서 인입은 백그라운드여야 하고 진행률·재개가 필요하다 — `sync_state` 가 재개를 이미 준다
- **프리픽스 캐시는 가끔만 잡힌다.** 같은 시스템 프롬프트(6,912 토큰)를 매번 보내는데 `cached_tokens` 가 32회 중 4회만 찍혔다. 잡히면 그 몫이 $0.3/1M 로 내려가 호출당 $0.02 (입력의 40%) 가 준다. 어림은 usage 가 말하는 대로 계산하고(안 잡힌 호출은 미스 단가), 실제 청구는 콘솔로 대조한다
- **잔액 반영이 늦다.** 호출 뒤 십여 분이 지나도 `/users/me/balance` 가 그대로다. 실행 끝의 잔액 줄은 참고만, 진짜 값은 다음 실행의 시작 잔액과 콘솔
